# Five-provider CLI

The execute/worker path supports OpenAI, DeepSeek, Qwen, Gemini and Claude.
Each Run freezes one provider and model. Role-level model mixing and cross-run
scientific evaluation are not implemented yet.

| Provider | Key environment variable | Model environment variable | Profile suffix |
|---|---|---|---|
| openai | OPENAI_API_KEY | CO_SCIENTIST_OPENAI_MODEL | online |
| deepseek | DEEPSEEK_API_KEY | CO_SCIENTIST_DEEPSEEK_MODEL | deepseek |
| qwen | DASHSCOPE_API_KEY | CO_SCIENTIST_QWEN_MODEL | qwen |
| gemini | GEMINI_API_KEY | CO_SCIENTIST_GEMINI_MODEL | gemini |
| claude | ANTHROPIC_API_KEY | CO_SCIENTIST_CLAUDE_MODEL | claude |

Use an API-accessible model ID, not a chat subscription name. Qwen currently uses
the mainland China DashScope endpoint; use a matching region credential.
Other native adapters request at most 8192 output tokens. The checked-in DeepSeek
profile explicitly requests 32768 tokens and low-effort thinking. Model support for JSON mode
varies; incompatible models fail through the existing durable retry mechanism.

## DeepSeek and OpenAI

From the repository root, activate the installed environment:

```bash
source .venv/bin/activate
```

Set credentials in your local terminal environment (do not commit them).
Then set explicit model IDs:

```bash
export CO_SCIENTIST_DEEPSEEK_MODEL='YOUR_DEEPSEEK_MODEL_ID'
export CO_SCIENTIST_OPENAI_MODEL='YOUR_OPENAI_MODEL_ID'

co-scientist run execute --run-id lens-deepseek-001 \
  --goal examples/lens_regeneration_goal.yaml \
  --profile configs/profiles/core_preview_deepseek.yaml \
  --provider deepseek --data-dir .co-scientist-deepseek

co-scientist run execute --run-id lens-openai-001 \
  --goal examples/lens_regeneration_goal.yaml \
  --profile configs/profiles/core_preview_online.yaml \
  --provider openai --data-dir .co-scientist-openai
```

Both use live PubMed and the same example goal. The DeepSeek example additionally
enables the context, abstract retrieval and repair settings below. For a controlled
provider comparison, align all profile settings except provider/model first.

### Live-run retrieval and scientific inputs

The DeepSeek example enables `scientific_context: true`. Newly scheduled review,
proximity, ranking and synthesis tasks include the referenced immutable hypothesis
contents and research goal, rather than only IDs and hashes. Full reviews also
receive the retrieved PubMed source records. To enable this for another live
provider, add the same flag to its profile.

`literature_search_queries` is an ordered list of up to five unique, nonblank
queries. The DeepSeek lens example restricts the first search to `lens regeneration`
or `lens epithelial` phrases in Title/Abstract and broadens only after an empty
result. `literature_sort: relevance` requests PubMed Best Match ordering.
The Supervisor schedules each attempt as a separate budgeted,
raw-first call. A crash after submission resumes without repeating that call.
If all queries return no PMIDs, the run ends explicitly as `failed` with reason
`literature_search_exhausted`; it does not silently fabricate evidence or bypass
novelty review. Other research topics should supply their own queries.

These settings are frozen in the run manifest. Existing runs retain their old
queries and task snapshots; start a new run to adopt the new context settings.
Legacy profiles with no query list retain their original single query.

`literature_content: abstracts` (enabled in the DeepSeek example) fetches PubMed
EFetch XML instead of ESummary JSON. XML is stored before parsing; the resulting
source records include structured abstract text, preserving section labels and
inline text. Each source reports `content_level: abstract` or `metadata`. Missing
abstracts remain null rather than being generated by an LLM. Identity mismatches,
duplicate PMIDs, XML entities and error envelopes are rejected. Abstract mode
requires live PubMed and `scientific_context: true`; legacy replay fixtures remain
metadata-only. The internal `summary` task/provider slot is retained for backward
compatibility, but `model_or_tool: efetch`, task content mode and raw XML distinguish
the abstract retrieval in the audit trail.

This follows the official [NCBI E-utilities EFetch documentation](https://www.ncbi.nlm.nih.gov/books/NBK25499/).

**Evidence limitation:** abstracts are not full text, and a nonempty retrieval is
not proof of relevance, mechanism validity or novelty. The current search is
run-level, not a systematic review of every hypothesis. Insufficient-evidence
results remain legitimate; do not force them to pass merely to complete the run.
Profiles omitting `literature_content` still use bibliographic metadata only.

To enable the same evidence path for another live model provider, add:

```yaml
scientific_context: true
literature_content: abstracts
literature_sort: relevance
literature_search_queries:
  - '"lens regeneration"[Title/Abstract]'
  - '"lens epithelial"[Title/Abstract] AND fibros*[Title/Abstract]'
```

These are examples, not a comprehensive search strategy. Use the same frozen
queries/settings across providers when designing controlled comparisons.

Negative full reviews (`needs_more_evidence` or `reject`) may legitimately omit
citations and novelty assessments; any citations they do claim must still come
from the retrieved source set. Passing reviews retain the stricter evidence
requirements. Once required reviews are collected, the scheduler uses the same
admission reducer to select candidates eligible for proximity checks. Rejected,
not-novel, unsafe or critically flawed candidates remain in the audit trail but
do not block other eligible candidates. Proximity/duplicate checks are still
mandatory before actual admission. With automatic review repair disabled or exhausted, the Core workflow pauses as
`needs_attention` / `review_requires_scientist_input` if too few eligible candidates
remain for its minimum candidate/anchor configuration. A model's `pass` paired
with nonempty `critical_flaws` is not sufficient for admission. The pause lists
the eligible IDs and each excluded candidate's blocking requirements. This is a
research-evidence boundary, not a successful scientific run. Re-running the same
worker without new evidence does not resolve it; use a revised research run.

New real-provider templates enable bounded review repair and scientific feedback:

```yaml
evolution:
  max_rounds: 3
  max_children_per_round: 2
meta_review:
  max_rounds: 2
  match_interval: 2
  max_children_per_round: 1
```

When too few candidates pass review, the Supervisor creates a repair task using
the immutable parents, persisted review feedback and the existing literature
snapshot. Children use fresh IDs and recorded parent links; all policy-required
reviews run again, including full novelty review when configured. Only eligible
children proceed to Proximity and admission, receiving a new initial rating.
Safety-blocked parents are excluded from automatic repair. Failed repairs remain
visible and the run pauses after the configured rounds. Existing runs and profiles
without this section retain `max_rounds: 0`; starting a new run adopts the setting.

The scheduler limits children by the remaining hypothesis and model-call budgets,
leaving room below the existing hard-stop thresholds for re-review. Every external
call still uses the durable budget ledger. Token and USD consumption cannot be
known exactly before a response; unknown pricing remains explicitly unpriced.
Review repair and feedback-driven Evolution share the same round cap. The feedback
path selects eligible parents referenced by a versioned scientific Meta-review,
not safety-blocked candidates. Both paths reuse one retrieved evidence window
rather than performing a fresh literature search per child.

For `scientific_context: true` runs with a finite call or match budget, a tournament
that has completed its minimum comparisons but has not converged now continues
one comparison at a time, alternating candidate and fixed-anchor comparisons.
Each new result creates a fresh evidence-bound stop checkpoint. Repeated anchor
comparisons keep distinct match IDs; checkpoints use the latest validated result
per frozen anchor. A hard-budget stop proceeds through stopping/finalization;
it does not imply scientific convergence. Legacy replay profiles keep their
fixed-round behavior. With `meta_review.max_rounds > 0`, a non-converged idle
checkpoint may schedule a scientific summary and at most one Evolution task per
feedback version. Children must repeat admission checks; subsequent comparisons
prioritize less-compared candidates and pairs. Budget, scientist stop and convergence
take precedence, so the round caps are not a promise of completed cycles. The loop
requires Research v1, enabled Evolution, and finite call and match budgets. Set
`meta_review.max_rounds: 0` to disable it; disable both round caps to turn off all
Evolution. Existing manifests remain frozen. See [the feedback contract and
offline acceptance tests](research-protocol.md#有界自动反馈闭环2026-09-19-验收).

With `scientific_context: true`, malformed/ungrounded model output is also retained
raw-first and pauses as `needs_attention` / `provider_output_invalid`. It is not
silently repaired into a scientific pass, and `worker run` does not automatically
spend more on the same failed output. Inspect the identified call's raw artifact
and revise the task/profile in a new run. This safety pause leaves the failed call
and pending tasks intact for audit; it is not full completion or finalization.
Actual literature and generated hypotheses may differ across runs; these are
initial functional trials, not a controlled scientific benchmark.

```bash
co-scientist run status lens-deepseek-001 --data-dir .co-scientist-deepseek
co-scientist worker run lens-deepseek-001 --data-dir .co-scientist-deepseek
co-scientist run export lens-deepseek-001 --data-dir .co-scientist-deepseek \
  --output lens-deepseek-001-export
```

Use a new run ID for a new experiment; retain the same data directory to resume.
Exports must target new directories. Terminal failed runs require a new run ID.
Raw provider envelopes are persisted before scientific JSON parsing. Invalid or
truncated scientific output is rejected. Usage records contain provider token counts;
USD remains unpriced and must not be interpreted as free usage.

## DeepSeek thinking and output limits

The DeepSeek profile accepts:

```yaml
providers:
  llm: deepseek
  literature: pubmed
  deepseek_generation:
    max_tokens: 32768
    thinking: enabled
    reasoning_effort: low
    timeout_seconds: 300
```

Thinking tokens consume the output allowance. A response ending with
`finish_reason: length` is rejected even if it contains partial JSON.
Set `thinking: disabled` for a non-thinking trial; the adapter omits
`reasoning_effort` in that mode. Supported efforts are low, high and max,
subject to the chosen model's API support.

Settings are validated and frozen in the Run manifest. Resuming uses the frozen
settings rather than subsequently edited YAML. Start a new Run ID to test changed
settings. Old manifests without generation settings retain the legacy 8192-token
request and the provider's default thinking behavior.
